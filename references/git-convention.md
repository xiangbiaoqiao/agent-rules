# Git 提交规范

> 提交信息是写给**下一个排查问题的人**看的，不是写给自己的。
> 半年后 `git log` 一翻，要能看出「哪次改动引入了这个 bug」。

---

## 0. 一句话原则

**一个提交只做一件事。** 混在一起的提交，review 不了、回滚不了、bisect 不定。

---

## 1. 提交信息格式

采用 Conventional Commits，**类型用英文、描述用中文**：

```
<type>(<scope>): <subject>

<body>

<footer>
```

- `type`：必填，见第 2 节
- `scope`：可选，模块名（`report` / `login` / `batch-cost`）
- `subject`：必填，中文，一句话说清做了什么
- `body`：可选，说明**为什么**这么改、有什么影响（不是复述代码）
- `footer`：可选，关联需求/缺陷编号、`BREAKING CHANGE`

示例：

```
fix(login): 修复汇总表把负数登录天数算成 0 的问题

统计 SQL 用了 ISNULL(SUM(x),0)，导致 -1 和 0 无法区分。
改为先判 NULL 再累加，并在 VO 注释里写明允许负值。
```

---

## 2. type 类型表

| type | 用途 | 例 |
|---|---|---|
| `feat` | 新功能 | `feat(report): 新增批次成本导出` |
| `fix` | 修 bug | `fix: 修复分页参数越界导致空列表` |
| `refactor` | 重构，**行为不变** | `refactor: 拆分 ReportService 的 300 行方法` |
| `perf` | 性能优化 | `perf: 商品猪成绩表加批次索引，查询从 8s 降到 200ms` |
| `style` | 格式调整，不影响逻辑 | `style: 统一缩进为 4 空格` |
| `docs` | 文档 | `docs: 补接口错误码说明` |
| `test` | 测试 | `test: 补登录日志汇总的边界用例` |
| `build` | 构建/依赖 | `build: 升级 hutool 到 5.8.12` |
| `ci` | CI 配置 | `ci: 加编译检查` |
| `chore` | 杂务 | `chore: 补充数据修复脚本` |
| `revert` | 回滚 | `revert: 回滚 #123 的改动` |

**type 用错最常见的情况**：把「改了行为」的重构写成 `refactor`。`refactor` 的定义是**外部行为完全不变**，一旦行为变了就是 `fix` 或 `feat`。

---

## 3. subject 怎么写

- 中文，**动词开头，说结果不说过程**：`修复登录超时`（✅） vs `修改了一下代码`（❌）
- 不超过 50 字，末尾**不加句号**
- 不要写「提交代码」「更新」「修改」这种没有信息的词
- 说清**影响范围**：`修复汇总表负数统计` 好过 `修复 bug`

```
❌ update
❌ 修改
❌ 修复了一些问题
✅ fix: 修复登录日志汇总表在跨月查询时丢数据
✅ feat(ai-report): 支持报告模板定版与历史版本对比
```

---

## 4. body 什么时候必须写

满足任一条件就要写 body：

- 改动**不直观**：为什么不用更简单的方案
- **有副作用**：影响其它模块、需要同步改配置、需要跑脚本
- **有取舍**：性能 vs 可读性、兼容 vs 干净
- 关联**线上问题**：贴一下现象和根因

body 里不要写「改了 A 文件加了 B 方法」——那是 `git diff` 干的事。

---

## 5. 一个提交的边界

**该在一个提交里的：**

- 功能代码 + 它对应的测试
- 接口改动 + 调用方的同步改动（否则中间状态编译不过）
- 数据修复 SQL + 引用它的说明

**必须拆开的：**

- 顺手修的格式 / 改名（和功能无关）→ 单独 `style` / `refactor`
- 依赖升级 → 单独 `build`（升级出问题能一键回滚）
- 两个不相干的需求 → 两个提交

判据：**这个提交能不能用一句话描述完？** 要用「并且」才能说清，就该拆。

## 6. 这个项目特有的坑：两个独立仓库

工作区里有**两个独立 git 仓库**，`cd` 错了就提交错地方：

| 目录 | 内容 |
|---|---|
| `pigdata/` | Java 后端 + JSP + 部分手写 JS |
| `pigdata-frontend/` | Vue2 前端源码 |

铁律：

- **提交前先 `git rev-parse --show-toplevel` 确认在哪个库**
- 前后端都改了 → **分两次提交**，各自 commit message
- `je-web/src/main/webapp/{pro,static,plugin}` 是构建产物，**不要单独为它提交**（除非确实直接改了产物理面的手写文件）
- 提交信息里分清：`feat(web)` 和 `feat(frontend)` 是两个库的事

---

## 7. 不该提交的东西

- 本地配置：`application-local.yml`、`.env`、IDE 配置
- 构建产物：`target/`、`dist/`（除非项目本来就把 dist 纳入版本管理）
- 日志：`*.log`
- 临时文件：`*.bak`、`*.tmp`、`.tmp-preview/`
- **密码、密钥、token**（含测试库连接串）

提交前 `git status` 扫一眼，别 `git add -A` 一把梭。

---

## 8. 分支命名

| 类型 | 格式 | 例 |
|---|---|---|
| 功能 | `feature/<简短描述>` | `feature/report-finalize` |
| 修复 | `fix/<简短描述>` | `fix/login-summary-negative` |
| 紧急修复 | `hotfix/<描述>` | `hotfix/cost-null` |

- 全小写 + 连字符，**不要中文、不要空格**
- 分支名和提交的 scope 尽量对应

---

## 9. 什么情况下不要自动提交

- **用户没让你提交，就不要提交、不要 push**（这是硬约束）
- 提交前必须让用户看到改了什么
- 不要 `git add -A` 代替用户判断；不要 `--amend` 已推送的提交
- 不要 `git push --force`，除非用户明确要求且确认了影响

---

## 10. 模拟提交前的自检

```
[ ] git rev-parse --show-toplevel → 确认在哪个仓库？
[ ] 这个提交能用一句话说清吗？（要说"并且"就拆）
[ ] type 选对了吗？（行为变了就不是 refactor）
[ ] subject 是中文 + 动词开头 + 说结果？
[ ] 有没有混进日志/临时文件/本地配置？
[ ] 有没有把密码、密钥带进去？
[ ] 编译过了吗？（没编译不许提交，更不许说"完成"）
```
