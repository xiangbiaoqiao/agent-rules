# 证据驱动调试规范

融合自 Trae `TRAE-debugger`（11 步科学调试法，已压缩为可执行版）。

---

## 0. 三道前置门（不满足就不要走这份流程）

**门 1 意图门**：用户是否**直接要求**「调试 / 排查 / 定位根因 / 采集运行时证据」？
- 「页面白屏」「接口很慢」「它崩了」——**只是症状，不算**。按普通任务处理。
- 「修一下这个」「优化一下」——不算。
- **不允许**因为你自己卡住了、命令失败了、改了几次没好，就自己开调试流程。调试意图必须来自用户。

**门 2 专有流程门**：项目有没有专门的调试手法、MCP、脚本？有就**优先用它的**，不要叠加本流程。

**门 3 复杂度门**：静态读代码/读配置能不能直接定因？
- 能 → 别调，直接读代码。
- 不能，且问题是间歇性/时序相关/并发/环境相关/状态迁移/需要运行时度量 → 才走。

## 1. 核心铁律

> **在拿到运行时证据之前，禁止修改任何业务逻辑。**

- 假设必须靠插桩日志证实/证伪，不能靠"读代码觉得是这里"。
- **第一处代码改动只能是插桩日志**，不能是修复。
- 哪怕 bug "显而易见"，也要先有证据。
- 修完必须有「修复前 vs 修复后」日志对比，证明问题消失且没引入新问题。

## 2. 流程

### 2.1 开档
在项目根建 `debug-<sessionId>.md`，`sessionId` 用语义化小写连字符（`login-500-error`、`cart-empty-bug`）。
这个文件是**第一处写操作**。里面维护：症状、复现步骤、环境、假设表、证据、结论、进度。

证据目录（高频 NDJSON 日志、env 文件）放**项目外**的临时目录，别污染被 watch 的工程树。

### 2.2 立假设（3–5 个，必须可证伪）
每个假设对应一个**具体观测点**。写完先给用户看，再动代码。

假设写不好的典型：「可能是代码有问题」「可能是环境问题」——不可证伪，等于没写。
好假设：「如果缓存 key 没带 tenantId，则不同租户会串数据 → 观测 `/cart` 返回的 tenantId 与请求头是否一致」。

### 2.3 插桩
- 只用项目**已有的**日志设施。禁止 `console.log` / `print` / `System.out`。
- 插桩用可折叠标记包起来，方便最后一次性删干净：
  - JS/TS `// #region debug-point <id>` … `// #endregion`
  - Java `// #region debug-point <id>` … `// #endregion`
  - Python `# #region debug-point <id>` … `# #endregion`
- 不新建 util 文件，一行内联解决。
- 需要集中收集多端日志时，可用本技能自带服务 `scripts/debug-server.py`（提供 `/health`、`/logs`、`/events`），但**先探测一次**，起不来就退回项目本地日志，别反复重试。

### 2.4 复现 + 收证
用能用的工具自己复现：跑测试、起服务、发请求、开浏览器。
**不要为了"要不要继续"反复问用户**。只有必须用户手动操作才能复现时，用一句话说明需要什么动作，然后停下等。

### 2.5 判定
逐条假设判定 `CONFIRMED` / `REJECTED` / `INCONCLUSIVE`，**引用具体日志行**作为依据。
全是 INCONCLUSIVE 且没有可用证据通道 → 记 `blocked`，清理插桩，退出流程，如实汇报，**不许猜根因**。

### 2.6 最小修复
证据指向根因后才改，改**最小范围**。不顺带重构。

### 2.7 验证 + 清理
- 同一复现路径再跑一遍，对比修复前后日志，确认失败信号消失且无新异常。
- 确认后**自动清理**插桩代码、关闭调试服务、删除 `debug-<sessionId>.md`（或按用户要求保留为记录），然后汇报根因。
- 用户中途叫停 → 立即清理并总结当前结论。

## 3. 输出要求

1. 3–5 条可证伪假设
2. 每次插桩/修复后的变更说明 + 具体操作路径（怎么复现）
3. 引用日志行的证据分析报告
4. 最小修复 + 前后对比结论
5. 清理摘要（根因 / 当前发现）
6. 证据门记录：假设表 + 证据来源 + `progress_status` + 每条假设的结论

## 4. 边界

不适用于：编译错误、类型错误、lint 失败、纯静态问题——这些直接看代码/看报错改，别开调试档案。
