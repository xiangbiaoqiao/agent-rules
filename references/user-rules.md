# 用户编码规则（P0 最高优先级）

来源：Trae `~/.trae-cn/memory/user_profile.md` 的「编码规范（跨项目跨语言，写任何代码一律遵守）」。
这是用户显式设定的、跨项目跨语言一律生效的硬规则。**与任何其他规范冲突时，以本文件为准。**

---

## 优先级顺序

```
P0  本文件（用户显式编码规则）
P1  项目现有代码风格与实际约定
P2  本技能其他 reference 的默认建议
```

**冲突处理**：P0 只管**新写的代码**；已存在的老代码不回头返工（见第 10 条）。
所以「项目变量都叫 `rows`」和「新变量要叫 `rowList`」不冲突——老的不动，新的按 P0。

---

## 十条硬规则

### 1. 方法 ≤ 80 行，单一职责
校验 / 主逻辑 / 清理 三段分层。

### 2. 主方法保持叙事性
3~7 步调用，或 ≤ 40 行。**不是越短越好**——拆成 5 个 3 行的小函数，可读性反而崩。

### 3. 拆分三问（全不满足就内联）
1. 会被复用吗？
2. 超过 20 行、或含复杂嵌套，值得给个名字吗？
3. 函数名能自解释吗？

三条都不满足 → **内联，禁止纯传话筒函数**（`doXxx()` 里只有一行 `return xxxService.xxx()`）。

### 4. 链式适度
- **适合链式**：`StringBuilder`、`Promise`、`Stream`、`Builder`
- **不要硬包**：单条件 `if` 别为了"统一风格"塞进链式
- **底线**：禁止为了链式牺牲可调试性

### 5. 嵌套 ≤ 2 层，卫语句提前 return
超过两层必须用 guard clause 拍平，不许往右一直缩进。

### 6. 命名硬性要求

**集合变量必须带类型后缀**：

| 类型 | 后缀 | 例 |
|---|---|---|
| 数组 / 列表 | `xxxList` / `xxxArr` | `orderList`、`idArr` |
| 映射 | `xxxMap` / `xxxObj` / `xxxDict` | `userMap`、`configDict` |

- 变量名必须自解释，**禁止** `a` `b` `c` `m` `ev` 这类。
- **豁免**：JSON / SSE 等协议字符串的 key 不算变量名，不受此限。
- ⚠️ **全局替换重命名必须防子串误伤**：把 `rows` 全局替换成 `rowList` 会把 `throws` 变成 `throwrowList`。替换后**必须编译验证**。

### 7. 集合返回空，不返回 null
返回 `Collections.emptyList()` / `[]` / `[]`（空列表）。null 返回把判空负担甩给每个调用方。

### 8. 日志与异常
- 日志用**占位符 / 结构化参数**，不拼字符串（`log.info("user {}", userId)`，不是 `"user " + userId`）
- `catch` 必须打**带上下文**的日志，**禁止吞异常**
- 对外错误消息用中文；技术细节（堆栈、内部标识）进日志

### 9. 常量与注释
- 魔法值常量化。
- **公共函数**写 Javadoc / docstring / 注释块：用途、参数、异常。
- **函数体内**的注释只写「为什么」，不写「做什么」。

### 10. 一次改动不重排别人的代码
只动自己改的那个方法。不顺手调格式、不顺手改命名、不顺手挪位置。

## 语言细则

### Java
- `List` 变量以 `List` 结尾，`Map` 变量以 `Map` 结尾
- slf4j 用 `{}` 占位符
- 常量 `private static final`

### JS / TS / Vue
- 常量 `UPPER_SNAKE_CASE` + `const`
- 模板字符串或占位符拼接，不搞 `+` 拼接
- Vue 组件内函数同样按叙事性拆分

### Python
- `list` 变量 `xxxList`，`dict` 变量 `xxxDict`
- 常量 `UPPER_SNAKE_CASE`
- 用 docstring，不在函数里堆行内注释

## 自检（每次交付前逐条过）

```
[ ] 每个方法 ≤80 行？主方法 3~7 步或 ≤40 行？
[ ] 有没有纯传话筒函数？（有就内联）
[ ] 链式有没有为了好看而牺牲可调试性？
[ ] 嵌套有没有超过 2 层？有没有该用卫语句的地方？
[ ] 集合变量带 List/Arr/Map/Obj/Dict 后缀了？
[ ] 有没有 a/b/c/m/ev 这种变量名？
[ ] 返回集合的地方，空场景返回的是空集合不是 null？
[ ] 日志是占位符不是字符串拼接？
[ ] catch 里打日志了吗？有吞异常吗？
[ ] 魔法值常量化了吗？
[ ] 公共函数有 Javadoc/docstring 吗？
[ ] 有没有动到不属于本次需求的老代码？
[ ] 做过全局替换重命名吗？编译验证过吗？检查过子串误伤吗？
```

## 附：需求处理偏好（同源，一并遵守）

用户画像里还有一段工作方式偏好，跟编码规范是同源设定的，一起固化：

1. **优先复用现有成熟能力，避免重复造轮子。**
2. **先对齐整体实现思路，再动手写代码。** 不要一上来就闷头改。
3. 遇到非核心问题主动跳过，优先保障核心功能跑通。
4. **方案要清晰可落地，先跑通最小可用版本，再逐步优化扩展。** 不要第一版就堆满抽象和扩展点。
5. 代码任务偏好**先验证方案可行性再落地**。
6. **修改内容要固化**，避免零散操作——改完就落盘，不要散落在对话里。
7. 部署时偏好提供**完整打包好的部署文件夹**，直接替换，避免零散改动。
