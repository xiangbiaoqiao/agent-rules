# 安全审查规范

融合自 Trae `TRAE-security-review`。仅在**用户要求安全审查 / 漏洞扫描 / 安全审计**时使用。
通用代码审查走 `review.md`；写代码时默认安全编码走 `security-general.md`。

---

## 0. 不可协商的原则

违反任一条的发现必须丢弃。

- **只用右侧（改动后）行号。**
- 区间形式 `[L_start, L_end]`，单行两端相同。
- **只管本次改动引入的面。** 改动前就存在且未被触碰的弱点，不在范围内。
- **可报 ⇔ 可证明可利用。** 说不清 (a) 攻击者可控输入从哪进 (b) 它到达哪个危险汇/边界，就不要报。
- **默认排除**：可用性问题（DoS/限流）、代码风格、测试与 fixture 代码。
- **置信度下限 0.8。** 低于此丢弃，或降级给人工。
- **不写补丁。** 只识别和解释，不在报告里贴替换代码。

## 1. 定范围

用户已给范围 → 原样使用，不放大也不缩小。
未给 → 问四选一：未提交改动 / 与某分支对比 / 某 MR-PR / 指定文件。
拒绝指定并要求直接开始 → 审 `origin/HEAD` delta。

## 2. 取 diff（四条探针）

```
git status                          # 工作区状态，找未跟踪/暂存异常
git diff --name-only origin/HEAD... # 触碰的文件面
git log --no-decorate origin/HEAD... # 提交时间线，还原意图
git diff --merge-base origin/HEAD   # 唯一权威变更内容
```

最后一条失败时按序降级：`git diff origin/HEAD...` → `git diff HEAD~1` → `git diff` → 回头问用户。

## 3. 上下文获取（出结论前强制）

只看片段推理禁止。每条候选发现必须有仓库级证据：

1. 用搜索定位：输入入口/信任边界、项目已有的 sanitizer/validator/鉴权工具
2. 用读取看**完整**文件 + 调用链邻居
3. 收集三类证据：
   - **源侧**：执行路径上具体的攻击者可控入口
   - **汇侧**：该值到达的危险操作、安全边界穿越、敏感数据外泄
   - **旁路**：附近代码是否已做编码/校验/鉴权；项目已有工具是否已化解

源侧或汇侧任一无法坐实 → 丢弃。

## 4. 意图还原

当作漏洞分类前，先推断作者为什么这么改：

- 新增错误处理/null 守卫 → 防御性重构，抬高"缺校验"类发现的门槛
- 算法/数据结构替换 → 行为变更，检查调用方不变量
- 依赖升级 + 适配层 → API 迁移，检查旧安全假设是否还成立
- 变量/模块重命名 → 语义变化小，通常无安全增量

与明显防御性意图相冲突的发现，需要更多证据而不是更少。

## 5. 只审这些类别

**不可信输入**：SQL 注入、命令注入、XXE、SSTI、NoSQL 注入、路径穿越
**认证授权**：鉴权绕过、越权（纵向/横向）、会话生命周期（固定/登出复用/未轮换）、JWT 误用（弱密钥、`alg=none`、缺 `aud`/`iss`/`exp`）、对象级越权（IDOR）
**密钥与密码学**：硬编码密钥/口令/token、弱算法（MD5/SHA1/ECB/RC4）、密钥不安全持久化、安全场景用可预测随机（`Math.random`）、证书校验被禁用/桩化
**代码执行**：不安全反序列化（`pickle`、`ObjectInputStream`）、YAML 加载任意类型、`eval`/`exec`/`Function`、XSS（受第 8 节框架豁免约束）
**敏感数据外泄**：密钥/凭证/PII 进日志或持久化、接口返回超出消费方需要、生产路径泄漏调试信息/堆栈

> 仅内网可利用**不降低**严重度。本地 RCE 仍是 HIGH。

## 6. 三遍审计（顺序执行，不许交叉）

**Pass A 项目安全基线**：项目已在用哪些 validator/转义/ORM/鉴权中间件/加密封装。**项目自己的模式就是比较基线。**

**Pass B 偏离图**：每个改动文件问——新代码用的是项目既有原语，还是引入了一套绕过它们的临时处理？偏离处产出最高。

**Pass C 源到汇追踪**：值从哪进 → 跨了哪些边界 → 路上有没有编码/校验/鉴权 → 落在哪。活不过 Pass C 的丢弃。

## 7. 严重度与置信度

| 严重度 | 触发 |
|---|---|
| HIGH | 可直接利用：RCE、鉴权绕过、大范围数据泄露、纵向越权 |
| MEDIUM | 特定但现实条件下可利用，影响实质 |
| LOW | 纵深防御缺口，直接影响有限（链路必须具体才报） |

| 置信度 | 含义 | 动作 |
|---|---|---|
| 0.90–1.00 | 具体攻击路径，仓库内可端到端追踪 | 报 |
| 0.80–0.89 | 已知漏洞模式，前置条件可合理满足 | 报 |
| 0.70–0.79 | 形态可疑，前置条件臆测 | **丢** |
| < 0.70 | 推测 | **丢** |

> **宁可漏报，不可滥报。** 噪音报告摧毁信任的速度，远快于漏掉一个纵深防御问题。

## 8. 硬性排除（不可按条豁免）

### 8.1 类别外
DoS/资源耗尽/限流缺口、过期第三方依赖、文档文件内的问题、"缺审计日志"/"缺加固"本身、测试与 fixture 代码、无具体可达路径的竞态/TOCTOU、任意形式的正则注入/ReDoS、日志含未过滤用户输入（仅密钥/凭证/PII 才算）、用户内容进 AI system prompt、SSRF 仅在 URL path 可控时（host 或协议可控才算）

### 8.2 框架/语言豁免
- React/Angular/Vue 默认 XSS 安全，需明确逃生口（`dangerouslySetInnerHTML`、`bypassSecurityTrust*`、`v-html`）
- 客户端 JS/TS 缺鉴权**不算**漏洞，鉴权在服务端
- 内存安全语言（Rust/Go/JVM/CLR/JS）的内存安全问题不报
- 脚本命令注入需可证的不可信输入入口
- `*.ipynb` 默认不可达
- 环境变量与 CLI flag 是可信输入，依赖它们的链路无效
- UUID 不可猜，不报缺校验
- GitHub Actions 问题需明确的不可信触发路径

### 8.3 细微 Web bug
Tabnabbing、XS-Leaks、原型污染、开放重定向——仅当链路高置信且 diff 内端到端可见，默认丢弃。

### 8.4 日志判例
记 URL 安全；记非 PII 业务值安全（哪怕"感觉敏感"）；只有泄漏密钥/凭证/PII 才报。

## 9. 输出

**无发现**：一行 `✅ 本次变更未发现可利用问题。`

**有发现**：一张表

| # | 类别 | 标题 | 严重度 | 置信度 | 证据（源 → 汇） | 建议 | 位置 |
|---|---|---|---|---|---|---|---|
| 1 | sql_injection | `lookup_user` 里的拼接查询 | HIGH | 0.92 | `req.query.q`(router L17) → 字符串拼接 → `db.query`(svc L88) | 改用项目已有的 `db.safe_query` 参数化 | [`services/user.py:[80,95]`](file:///abs/path#L80-L95) |

- 类别用 snake_case：`xxe` `idor` `unsafe_deserialization` `weak_crypto` …
- 证据必须同时含源和汇，用 `→` 分隔
- 位置用右侧行号 + `file:///...#Lx-Ly`
- 建议是散文，不是代码
- 排序：严重度降序，再置信度降序

## 10. 出表前自检（任一为否即删该行）

```
[ ] 位置是改动后行号？
[ ] 是本次 diff 引入或加重的，不是既有未触碰的？
[ ] 证据里源和汇都在？
[ ] 置信度 ≥ 0.80？
[ ] 通过了第 8 节全部硬性排除？
[ ] 建议只有散文，没有代码补丁？
```
